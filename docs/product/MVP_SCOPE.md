# MVP 范围与发布边界

> Status: Proposed<br>
> Owner: 角色 A<br>
> Reviewers: 角色 B<br>
> Last Updated: 2026-08-10

## 1. 推荐系统结论

两份原始材料对 AI 范围存在冲突。角色 A 已确认推荐能力采用“规则算法冷启动 + 平台自训练轻量模型”的路线，通用大模型不参与最终匹配分数。

版本边界如下：

- P0：可解释规则算法、完整推荐事件记录和真实组队闭环；
- P1：数据质量达到门槛后训练轻量排序模型，先影子验证再逐步启用；
- 可选增强：生成式 AI 仅辅助文案，不阻塞 P0/P1，也不能改变规则和模型分数；
- 禁止将未训练、未评估的模型或通用大模型调用包装成已验证的智能推荐。

相关决策见 [ADR-0002](../decisions/ADR-0002-mvp-ai-scope.md)。

## 2. P0：上线必需

| 能力 | 范围 | 退出标准 |
| --- | --- | --- |
| 登录与同意 | 微信登录、服务条款/隐私政策同意、退出登录 | 新用户可合法进入，拒绝同意时不创建正式账号 |
| 能力名片 | 基础信息、技能、经历、偏好、可投入时间 | 用户可创建、修改并控制必要字段的展示 |
| 项目管理 | 草稿、发布、编辑、关闭；岗位和人数 | 项目方可完成一次完整招募发布并关闭招募 |
| 项目大厅 | 列表、详情、分类、基础筛选和分页 | 用户能稳定找到符合筛选条件的已发布项目 |
| 人才大厅 | 已公开名片列表、详情和基础筛选 | 项目方只能查看用户明确公开的信息 |
| 基础匹配 | 结构化规则评分、硬约束过滤、原因展示 | 同一输入结果可重复、可解释、可测试 |
| 推荐数据基线 | 记录推荐曝光、详情访问、沟通、邀请与组队结果 | 事件有版本、去重、最小化数据和可追溯来源 |
| 站内沟通 | 首次留言/会话、邀请、接受或拒绝 | 用户可从匹配结果进入沟通并确认组队意向 |
| 安全治理 | 举报、拉黑、内容下架入口、账号注销 | 被拉黑用户不能继续联系；注销流程可执行 |
| 可观测性 | 关键事件、错误日志、健康检查 | 能定位发布、匹配和沟通主链路失败原因 |

## 3. P1：自训练轻量排序模型

- 基于平台自身的合规行为与组队结果构建训练集；
- 先训练可解释基线模型，再评估梯度提升树或学习排序模型；
- 模型只重排通过硬约束过滤的候选，规则算法始终作为冷启动和故障兜底；
- 通过时间切分离线评估、影子运行和小流量实验后才允许生产启用；
- 每次推理记录模型版本，支持立即切回规则排序；
- AI 辅助生成个人简介、团队缺口建议和自然语言润色作为独立可选能力，必须由用户确认；
- 经用户授权的获奖证明上传和人工/半自动认证；
- 用户评价与信誉机制（必须先完成反滥用设计）；
- 更完整的赛事资讯和运营入口。

P1 模型和生成式功能必须分别支持关闭；模型或外部服务不可用时，P0 规则匹配仍应工作。训练与上线流程见 [ML_RECOMMENDER.md](../architecture/ML_RECOMMENDER.md)。

## 4. 明确不进入首版

- 高校管理后台、企业招聘端和付费订单；
- Elasticsearch、Milvus、Chroma 等独立集群，除非有数据证明现有查询无法满足；
- 端到端深度推荐模型、在线实时训练和未经评估的 embedding 相似度；
- 复杂实时聊天能力（已读回执、群聊、音视频、文件传输）；
- 自动履历真实性判定和自动信誉处罚；
- 跨校统一认证、项目孵化和赛事辅导交易。

## 5. 发布门槛

- P0 需求有可追溯的验收测试；
- 登录、项目发布、匹配、沟通和组队确认主路径通过；
- 服务端完成资源级授权校验，不依赖前端隐藏按钮；
- 隐私政策、服务条款、注销、举报和拉黑路径可用；
- 不存在已知高危安全问题或会造成数据损坏的问题；
- 监控、备份、回滚和负责人信息已填写；
- 角色 A 完成产品验收，角色 B 完成后端、安全和部署验收。

## 6. 变更规则

增加 P0 功能必须说明：目标用户问题、为何阻塞上线、工作量、依赖、测试和延期影响。未经双方确认，不得用“顺便做”扩大首版范围。
