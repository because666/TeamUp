## 1. 目标

本 PRD 将原始 PDF 转为可开发、可测试的需求基线。所有需求使用稳定 ID；实现、测试、任务文件和评审记录（及可选 PR）应引用这些 ID。

首版目标是验证“资料建立 -> 项目/人才发现 -> 可解释匹配 -> 沟通 -> 组队确认”的真实使用闭环，并为后续自训练轻量推荐模型积累合规、可解释的反馈数据。

后端模块、权限、数据一致性、运行要求和交付阶段见 [后端 PRD](BACKEND_PRD.md)。本文继续作为产品行为和用户验收的权威来源，后端 PRD 不得静默改变本文需求。

## 2. 用户与权限

首版只有一个学生账号类型，按当前行为承担不同身份：

- 普通用户：维护自己的能力名片，浏览项目，发起沟通；
- 项目创建者：管理自己创建的项目、岗位和邀请；
- 项目成员：查看自己已加入项目的必要信息；
- 运营管理员：处理举报和违规内容，权限必须独立且有审计记录。

任何“创建者”权限必须基于资源所有权在服务端判断，不能只相信客户端传入的用户 ID。

## 3. 核心流程

### FLOW-01：成员寻找项目

登录 -> 完善能力名片 -> 浏览/筛选项目 -> 查看匹配原因 -> 发起沟通 -> 接受邀请或确认加入。

### FLOW-02：项目方寻找成员

登录 -> 创建项目与岗位 -> 发布 -> 查看候选人才/匹配原因 -> 发起邀请 -> 对方接受 -> 更新岗位状态。

### FLOW-03：安全退出

用户举报或拉黑 -> 平台阻断后续联系 -> 管理员处理 -> 用户可查看处理状态；用户也可申请注销并按政策删除或匿名化数据。

## 4. 功能需求

### 4.1 登录与账号

#### AUTH-001 微信登录

- 客户端获取一次性登录凭证，服务端与微信接口换取身份标识。
- 服务端签发自己的会话凭证，不向客户端暴露第三方密钥。
- 首次登录必须完成服务条款和隐私政策同意。

验收标准：

- 有效凭证可创建或登录同一账号；无效、过期或重复使用凭证返回明确错误。
- 未同意隐私政策的用户不能发布、沟通或进入人才公开列表。
- 日志不记录完整登录凭证和会话令牌。

#### AUTH-002 账号与会话管理

- 用户可退出当前会话并申请注销账号。
- 服务端可撤销会话；敏感操作需要有效身份。

验收标准：退出后旧凭证不可继续调用受保护接口；注销进入可审计流程并反馈处理结果。

### 4.2 能力名片

#### PROF-001 编辑能力名片

字段包括昵称、院校、专业、年级、技能标签、项目/赛事/科研经历、合作场景、队长/队员偏好和可投入时间。

验收标准：

- 必填项、长度和枚举值均有服务端校验。
- 用户只能修改自己的名片。
- 未经用户确认，AI 生成内容不得直接覆盖用户输入。

#### PROF-002 名片可见性

- 用户可控制是否进入人才大厅。
- 联系方式默认不公开；沟通通过站内机制发起。

验收标准：关闭公开后，名片不再出现在新的人才搜索和推荐结果中；已有合规记录按隐私政策处理。

### 4.3 项目与岗位

#### PROJ-001 创建和发布项目

项目字段包括标题、简介、方向、适配赛事、项目阶段、团队信息；每个招募岗位包含名称、技能、人数、投入时间和说明。

验收标准：

- 项目可保存草稿；只有字段完整且至少有一个开放岗位时可发布。
- 只有创建者可编辑、发布、关闭或重新开放项目。
- 发布后关键变更保留更新时间；已关闭项目不进入新匹配。

#### PROJ-002 项目可信信息

- 现有团队与履历信息必须区分“用户填写”和“已认证”。
- 不得仅因 AI 生成或用户上传就标为已认证。

### 4.4 发现与检索

#### DISC-001 项目大厅

支持分页浏览和按方向、赛事、技能、项目阶段、状态筛选；排序至少支持最新发布。

验收标准：筛选组合稳定返回符合条件的公开项目；无结果、加载失败和下一页均有明确状态。

#### DISC-002 人才大厅

仅展示明确选择公开且状态正常的能力名片，支持技能、方向、合作偏好和可投入时间筛选。

验收标准：被拉黑双方互不出现在可联系结果中；非公开字段不出现在响应数据中。

### 4.5 匹配

#### MATCH-001 基础可解释匹配

- 先应用硬约束过滤，再按技能、方向、时间、专业和经历计算结构化分数。
- 返回分项依据、满足项和缺失项；不得只返回总百分比。
- 具体权重和缺失值处理见 [MATCHING.md](../architecture/MATCHING.md)。

验收标准：

- 相同版本、相同输入得到相同结果。
- 不满足不可协商硬约束的候选不会被列为高匹配。
- 返回匹配规则版本，测试覆盖边界值和资料缺失场景。

#### MATCH-002 双向匹配入口

成员可从项目发现候选岗位，项目创建者可从岗位发现候选成员。两个方向必须使用兼容的规则和隐私过滤。

#### MATCH-003 推荐反馈数据

- 服务端记录推荐版本、候选集合、实际曝光、详情访问、发起沟通、邀请、接受/拒绝和组队确认等最小必要事件。
- 私信正文、联系方式、举报原文和无关敏感属性不得进入训练特征。
- “未点击”不能直接视为负样本，必须区分未曝光、曝光位置和观察窗口。

验收标准：事件可去重、可追溯到规则/模型版本；用户注销和数据保留策略能够作用于训练数据及派生数据。

#### MATCH-004 轻量机器学习排序（P1）

- 使用平台自身合规数据离线训练小型排序模型，推荐从逻辑回归基线开始，再按数据证明评估梯度提升树或 learning-to-rank。
- 模型只能重排通过 MATCH-001 硬约束的候选，不能改变权限、拉黑、项目状态和必需条件。
- 模型输出包含版本、分数和可映射为安全解释的特征贡献；低置信度、冷启动或故障时回退规则算法。

验收标准：通过时间切分离线评估、影子流量比较、公平性检查和可回滚验证；生产启用门槛由单独模型评审记录确认。

### 4.6 沟通与组队

#### MSG-001 站内会话

用户可从项目、人才或匹配结果发起一次站内会话。首版只要求文本消息和必要的系统状态消息。

验收标准：只有会话参与者可读取消息；被拉黑后不能发送新消息；分页顺序稳定。

#### TEAM-001 团队邀请

项目创建者可针对开放岗位邀请用户；被邀请者可接受、拒绝或忽略。

验收标准：

- 邀请必须关联项目和开放岗位。
- 重复接受不会产生重复成员记录。
- 岗位满员、项目关闭或邀请过期后不能接受。
- 接受成功后形成可统计的组队记录。

### 4.7 生成式 AI 辅助功能

以下能力与推荐模型分离，均为可选增强，不参与最终匹配分数。

#### AI-001 个人简介辅助生成

基于用户明确输入生成草稿，展示“AI 生成”提示，由用户编辑并确认后保存。不得捏造奖项、经历、院校或技能。

#### AI-002 团队缺口建议

基于项目和已填写团队信息给出岗位建议，结果不自动创建岗位，不替项目方作出人员决定。

#### AI-003 匹配解释润色

只能润色规则或模型服务已提供的结构化因素，不得自行修改分数、编造匹配原因或暴露其他用户非公开数据。

生成式 AI 不可用时，P0 流程必须使用模板化说明并保持可用。

### 4.8 安全治理

#### SAFE-001 举报与拉黑

- 用户可举报用户、项目和消息，并选择原因和补充说明。
- 用户可拉黑另一用户，立即阻断新消息和新邀请。

验收标准：举报内容仅对有权限的管理员可见；拉黑校验在服务端执行；处理动作进入审计记录。

#### SAFE-002 内容状态

项目、名片和消息至少支持正常、隐藏/下架、删除状态。删除和审计保留策略见安全文档。

## 5. 非功能需求

| ID | 要求 |
| --- | --- |
| NFR-SEC-001 | 所有受保护接口执行身份与资源级授权校验 |
| NFR-SEC-002 | 密钥只存于服务端安全配置，不进入仓库、客户端包和日志 |
| NFR-PRIV-001 | 个人数据最少收集、目的明确、可查询更正并支持注销处理 |
| NFR-REL-001 | 写操作支持幂等或重复请求保护，避免重复邀请和重复成员 |
| NFR-OBS-001 | 核心链路有结构化错误日志、请求标识和健康检查 |
| NFR-PERF-001 | 性能目标在完成真实接口原型后通过 ADR 确认，不得虚构数值 |
| NFR-COMP-001 | 小程序端遵循微信平台规则和适用的个人信息保护要求 |

## 6. 建议埋点

事件仅记录业务所需的最小字段，禁止把简介、消息正文、令牌等直接发送到分析平台。

- `profile_completed`
- `project_published`
- `project_viewed`
- `match_result_viewed`
- `recommendation_impression`
- `conversation_started`
- `team_invitation_sent`
- `team_invitation_accepted`
- `report_submitted`
- `account_deletion_requested`

埋点名称、属性和指标口径在接入分析工具前单独评审。

## 7. 验收与变更

- 每个实现任务必须引用至少一个需求 ID。
- 需求变更必须同时修改验收标准、任务文件和受影响的接口/数据文档。
- 涉及范围、权限、安全或技术栈的重大变化必须新增 ADR。
- 本文档从 `Proposed` 变为 `Confirmed` 前，需要角色 A 确认产品范围、角色 B 确认技术可行性与安全边界。
