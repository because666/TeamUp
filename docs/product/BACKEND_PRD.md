## 1. 文档定位

本文定义 TeamUp 后端在 MVP 阶段必须交付的用户行为、服务端规则、权限边界、数据一致性、非功能要求和验收条件。它是后端任务拆分与验收入口，不替代以下权威规范：

- 产品行为与用户价值以 [产品 PRD](PRD.md) 和 [MVP 范围](MVP_SCOPE.md) 为准；
- HTTP 路径、DTO、状态码和示例以 [API 契约](../architecture/API_CONTRACT.md) 及未来 OpenAPI 文件为准；
- 实体、关系和迁移原则以 [数据模型](../architecture/DATA_MODEL.md) 为准；
- 匹配计算以 [匹配设计](../architecture/MATCHING.md) 为准；
- 个人信息、鉴权和日志要求以 [安全与隐私规范](../security/SECURITY_AND_PRIVACY.md) 为准；
- 技术框架以 [ADR-0001](../decisions/ADR-0001-backend-framework.md) 为准。

当本文与已确认规范冲突时，按仓库真值优先级处理，不得通过实现静默改变产品或安全规则。本文中的 `TBD` 和 `GAP-*` 必须在对应实现任务开始前由指定负责人确认。

## 2. 产品背景与后端目标

TeamUp 面向高校学生竞赛、科研和创业项目，核心闭环是：

```text
微信登录与同意
-> 建立能力名片
-> 发布项目和岗位
-> 发现与可解释匹配
-> 双方同意交换联系方式和邀请
-> 接受邀请并形成成员关系
-> 记录合规反馈用于后续推荐优化
```

后端目标：

| ID | 目标 | 验收信号 |
| --- | --- | --- |
| `BE-GOAL-001` | 提供稳定的 `/api/v1` 业务接口 | OpenAPI 与实际响应通过契约测试 |
| `BE-GOAL-002` | 在服务端统一执行身份、资源和状态授权 | P0 对象接口通过未认证、非所有者和 IDOR 测试 |
| `BE-GOAL-003` | 保障邀请、成员和项目状态一致 | 重复/并发请求不产生重复成员或超额岗位 |
| `BE-GOAL-004` | 提供可解释、可回退的规则匹配 | 相同版本和输入结果稳定，返回结构化因素 |
| `BE-GOAL-005` | 保护学生资料和联系方式 | 响应、日志、测试数据和第三方调用满足最小化要求 |
| `BE-GOAL-006` | 支撑定位、发布和恢复 | 健康检查、请求 ID、结构化日志、迁移、备份和回滚可执行 |

## 3. 范围与优先级

### 3.1 P0 必须交付

- 微信登录、平台会话、退出和注销申请；
- 能力名片读取、编辑、公开控制和公开详情；
- 项目、岗位、草稿、发布、编辑、关闭和成员关系；
- 项目大厅、人才大厅、筛选、稳定排序和游标分页；
- 规则匹配、硬约束、解释因素和推荐曝光记录；
- 私有联系名片、联系方式交换申请、邀请、接受与拒绝；
- 举报、拉黑、取消拉黑和必要审计；
- MySQL 迁移、约束、测试数据、健康检查、日志和部署基线；
- local、test、staging、production 环境隔离；
- 契约、单元、集成、安全、E2E 和发布烟测。

### 3.2 P1 后续交付

- 使用平台合规行为数据训练轻量排序模型；
- 模型登记、影子运行、小流量启用和规则回退；
- 可关闭的生成式 AI 文案辅助；
- 经单独评审的资料证明上传与认证；
- 更完整的运营治理和指标分析。

### 3.3 明确不在 MVP

- 微服务拆分和消息中间件；
- Elasticsearch、Milvus、Chroma 等独立搜索/向量集群；
- 在线实时训练、端到端深度推荐和未经评估的 embedding 排序；
- 群聊、音视频、文件消息、已读回执等复杂即时通信；
- 自动录取、自动处罚、自动履历认证；
- 企业招聘、付费订单、高校管理后台和跨校统一认证。

## 5. 用户、角色与权限

### 5.1 业务身份

| 身份 | 定义 | 后端能力 |
| --- | --- | --- |
| Guest | 无有效平台会话 | 仅访问明确允许的公开/登录前能力 |
| User | 已认证学生用户 | 管理自己的能力/联系名片，浏览允许内容，发起联系方式交换 |
| Project Owner | 当前用户是项目 `owner_id` | 管理自己的项目、岗位和邀请 |
| Project Member | 当前用户有有效成员关系 | 查看项目成员可见信息 |
| Contact Exchange Participant | 当前用户是交换申请 requester 或 recipient | 按申请状态查看摘要；仅 `ACCEPTED` 后查看对方联系名片 |
| Operations Admin | 独立授予的运营权限 | 处理举报和内容状态，所有操作审计 |

### 5.2 授权矩阵

| 资源/动作 | Guest | User | Owner/Participant | Admin |
| --- | --- | --- | --- | --- |
| 微信登录 | 允许 | 允许重新登录 | 允许重新登录 | 允许重新登录 |
| 编辑自己的名片 | 禁止 | 允许 | 允许 | 不默认代改 |
| 查看公开名片 | 产品策略 `TBD` | 按公开和拉黑过滤 | 同左 | 仅治理所需 |
| 创建项目草稿 | 禁止 | 允许 | 允许 | 不默认代建 |
| 编辑/发布/关闭项目 | 禁止 | 仅自己的项目 | Owner 允许 | 治理动作走独立接口/审计 |
| 查看/处理联系方式交换 | 禁止 | 仅自己的发出/收到记录 | requester 可取消，recipient 可接受/拒绝 | 非治理场景禁止 |
| 创建邀请 | 禁止 | 仅自己项目开放岗位 | Owner 允许 | 不默认代发 |
| 接受/拒绝邀请 | 禁止 | 仅邀请接收者 | 接收者允许 | 不默认代处理 |
| 举报/拉黑 | 禁止 | 允许针对合法目标 | 允许 | 举报处理独立授权 |

所有权限必须在服务端执行。客户端传入的 `userId`、`ownerId`、角色、隐藏按钮或页面来源不能作为授权依据。对无权访问的敏感资源，错误响应不得泄露资源是否存在。

## 6. 通用 API 要求

### 6.1 协议与响应

- 基础路径：`/api/v1`；
- 生产环境只允许 HTTPS；
- 内容类型：`application/json; charset=utf-8`；
- 时间使用 ISO 8601 UTC；
- ID 对客户端是不透明字符串；
- 每个响应返回 `requestId`；
- 成功响应使用 `data`、`meta`、`requestId`；
- 错误响应使用 `error.code`、`error.message`、`error.details`、`requestId`；
- 客户端行为只能依赖稳定 `error.code`，不能解析 `message`。

### 6.2 认证与会话

- 微信一次性登录凭证只发送给后端，并且不能复用；
- 后端与微信接口交换身份标识，微信密钥不能进入客户端、仓库或日志；
- 后端签发并验证平台自己的访问凭证；
- 受保护接口使用 `Authorization: Bearer <token>`；
- `401` 表示未认证或会话失效，`403` 表示已认证但无权执行；
- token 类型、有效期、刷新、撤销和多端策略为 `GAP-BE-AUTH-01`，必须在认证实现前确认；
- local/test 登录替代方案必须仅在非生产环境启用，且不能接受生产密钥。

### 6.3 校验

服务端必须校验：

- JSON 类型、必填、长度、数值范围和枚举；
- 资源关系、所有权、状态机和可见性；
- 不透明 ID 格式和资源边界；
- 纯文本/允许列表内容；
- 分页上限、筛选字段和排序白名单；
- 外部凭证、幂等键和版本字段。

前端校验只用于体验，不能替代服务端校验。

### 6.4 分页、排序和过滤

- 列表默认使用不透明游标；
- 返回 `nextCursor` 和 `hasMore`；
- 排序必须稳定，必要时以唯一 ID 作为最后排序键；
- 未知筛选或排序字段返回 `VALIDATION_ERROR`；
- `limit` 默认值和上限为 `TBD`，必须基于接口原型和性能验证确认；
- 游标编码不得包含可被客户端依赖或篡改的数据库实现细节。

### 6.5 幂等与并发

- 登录凭证交换、联系方式交换申请/处理、创建邀请、接受邀请、推荐曝光等重复提交场景必须定义去重策略；
- 需要幂等保护的接口使用 `Idempotency-Key` 或等效服务端请求标识；
- 相同 key、相同请求返回相同业务结果；相同 key、不同请求返回冲突；
- 资源更新使用 `version` 或等效乐观锁；
- 版本冲突返回 HTTP `409` 和稳定错误码；
- 接受邀请必须在单一事务中重新检查项目、岗位、邀请、容量和成员唯一性。

### 6.6 错误码候选目录

下表是进入 OpenAPI 评审的候选集合，正式真值由 API 契约确认：

| Code | HTTP | 语义 |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400/422，`TBD` | 请求字段或业务输入无效 |
| `UNAUTHENTICATED` | 401 | 缺少有效会话 |
| `SESSION_EXPIRED` | 401 | 会话已过期或撤销 |
| `FORBIDDEN` | 403 | 已认证但无操作权限 |
| `RESOURCE_NOT_FOUND` | 404 | 资源不存在或按安全策略不可见 |
| `VERSION_CONFLICT` | 409 | 乐观锁版本冲突 |
| `IDEMPOTENCY_CONFLICT` | 409 | 幂等键与不同请求冲突 |
| `RATE_LIMITED` | 429 | 超过接口频率限制 |
| `CONSENT_REQUIRED` | 403 | 未满足当前条款/隐私同意要求 |
| `PROFILE_INCOMPLETE` | 409 | 业务动作要求完成名片 |
| `PROFILE_NOT_PUBLIC` | 404/403，`TBD` | 名片未公开或不可见 |
| `PROJECT_NOT_EDITABLE` | 409 | 项目当前状态不可编辑 |
| `PROJECT_NOT_PUBLISHABLE` | 409 | 项目或岗位未满足发布条件 |
| `PROJECT_CLOSED` | 409 | 已关闭项目不接受该动作 |
| `ROLE_FULL` | 409 | 岗位容量已满 |
| `INVITATION_NOT_ACTIONABLE` | 409 | 邀请已处理、过期或不可接受 |
| `CONTACT_CARD_REQUIRED` | 409 | 需要先填写自己的私有联系名片 |
| `CONTACT_REQUEST_NOT_ACTIONABLE` | 409 | 联系申请已处理或当前状态不允许该动作 |
| `CONVERSATION_FORBIDDEN` | 403 | 历史兼容会话：当前用户不是有效参与者 |
| `USER_BLOCKED` | 403/409，`TBD` | 拉黑关系阻止联系方式交换或邀请 |
| `EXTERNAL_SERVICE_UNAVAILABLE` | 503 | 微信或其他必要外部服务暂不可用 |
| `INTERNAL_ERROR` | 500 | 未映射内部错误，不暴露内部细节 |

## 7. 功能需求

### 7.1 系统与运行基线

#### `BE-SYS-001` 应用初始化

后端必须以 FastAPI 模块化单体实现，并建立 `services/api`、目录级 `AGENTS.md`、依赖锁定、配置加载、数据库迁移、OpenAPI、测试和容器启动基线。

验收标准：

- 全新克隆可按 `DEVELOPMENT.md` 的实际命令启动；
- 运行时和依赖版本被锁定；
- local/test 不依赖生产数据或生产凭证；
- 生产调试模式默认关闭；
- OpenAPI 可生成并由 CI 检查。

#### `BE-SYS-002` 健康与可观测性

后端必须提供不泄露内部信息的存活和就绪检查，并为每个请求生成/透传请求 ID、结构化记录结果与耗时。

验收标准：

- 存活检查不依赖所有外部服务；
- 就绪检查能反映必要依赖是否可用；
- 日志能通过 `requestId` 定位主链路失败；
- 日志不包含 token、微信凭证、密钥、联系方式值、完整历史私信和完整未公开资料；
- 指标阈值和告警条件在 staging 基线后确认，不虚构性能数字。

### 7.2 登录与账号

#### `BE-AUTH-001` 微信登录（API-AUTH-01 / AUTH-001）

- 接收客户端新获取的一次性微信凭证和当前有效同意版本；
- 调用微信接口交换稳定身份标识；
- 对同一微信身份查找或创建唯一用户；
- 只有满足同意要求时建立正式平台会话；
- 返回平台凭证和前端导航所需的最小用户/名片状态；
- 微信失败时不创建半完成会话，不伪造成功。

验收标准：有效凭证重复登录映射同一账号；无效、过期和重复使用凭证返回稳定错误；同意缺失不能进入受保护业务；日志完成脱敏；外部超时受控且可重试。

#### `BE-AUTH-002` 退出和会话撤销（API-AUTH-02 / AUTH-002）

- 撤销当前平台会话；
- 重复退出不产生额外副作用；
- 已撤销凭证不能继续访问受保护接口；
- 登出事件记录最小安全审计信息。

#### `BE-AUTH-003` 注销申请（API-AUTH-03 / AUTH-002）

- 创建可审计的注销请求；
- 阻止重复并行申请或返回已有申请状态；
- 按政策进入 `DELETION_PENDING`，而不是即时无审计硬删除；
- 数据保留、删除、匿名化和取消窗口为 `GAP-BE-PRIV-01`，上线前必须确认；
- 处理范围覆盖推荐训练原始和派生数据。

### 7.3 能力名片

#### `BE-PROF-001` 获取自己的名片（API-PROF-01 / PROF-001）

- 只返回当前用户自己的完整可编辑名片；
- 明确区分尚未创建、部分完成和已完成；
- 返回服务端确认的 `version`、完整状态和公开状态；
- 不返回微信身份、密钥或其他用户数据。

#### `BE-PROF-002` 更新自己的名片（API-PROF-02 / PROF-001/002）

- 校验昵称、院校、专业、年级、技能、经历、合作偏好、可投入时间、简介和公开选择；
- 具体长度、枚举、必填和公开字段为 `GAP-BE-PROF-01`，需与角色 A 确认；
- 只能更新当前用户资料；
- 使用乐观锁防止静默覆盖；
- AI 草稿只有用户确认后才能作为普通内容保存，不能自动标记经历为已认证；
- 保存与公开是两个不同语义，默认公开策略以产品契约为准。

验收标准：非法字段有稳定错误详情；旧版本返回 `409`；不能修改他人名片；关闭公开后不再进入新搜索和匹配结果。

#### `BE-PROF-003` 获取公开名片（API-PROF-03 / PROF-002）

- 仅返回目标用户明确公开的字段；
- 过滤非活跃账号、非公开名片和双方拉黑关系；
- 联系方式、微信身份、内部匹配特征和举报状态不得返回；
- 不存在与不可见的错误策略避免泄露资源存在性。

### 7.4 项目、岗位和成员

#### `BE-PROJ-001` 创建项目草稿（API-PROJ-01 / PROJ-001）

- 当前用户自动成为 owner，不接受客户端指定 owner；
- 支持项目字段和至少后续可关联的岗位结构；
- 草稿默认 `DRAFT`，不得进入大厅或匹配；
- 返回不透明 `projectId`、状态和 `version`；
- 项目/岗位使用嵌套写入还是独立端点为 `GAP-PROJ-01`，实现前必须进入 API 契约。

#### `BE-PROJ-002` 获取项目详情（API-PROJ-02 / PROJ-001）

- 根据 Guest、普通用户、成员和 owner 返回不同视图；
- 公开视图不返回管理字段和非公开成员资料；
- owner 管理视图可返回草稿、岗位和版本；
- 被隐藏、已删除、未公开或被拉黑资源按安全策略处理；
- 公开/owner/发布结果 DTO 边界属于 `GAP-PROJ-04`。

#### `BE-PROJ-003` 更新项目（API-PROJ-03 / PROJ-001）

- 只有 owner 可以更新；
- 校验项目状态、字段、岗位人数、技能和时间要求；
- 使用 `version` 乐观锁；
- 修改项目与岗位必须保证事务一致性；
- 已发布项目允许修改的字段范围为 `GAP-BE-PROJ-01`，需产品评审。

#### `BE-PROJ-004` 发布项目（API-PROJ-04 / PROJ-001）

- 只有 owner 可以发布自己的 `DRAFT`；
- 项目必填字段完整；
- 至少有一个 `OPEN` 岗位；
- 每个开放岗位 `headcount > 0` 且满足字段校验；
- 状态原子转换为 `PUBLISHED` 并记录发布时间；
- 重复请求不能重复执行副作用；
- 响应丢失后可通过项目详情确认真实状态。

#### `BE-PROJ-005` 关闭项目（API-PROJ-05 / PROJ-001）

- 只有 owner 可以关闭已发布项目；
- 关闭后不进入新发现和匹配，不接受新邀请；
- 已有成员、会话和审计记录按保留策略处理；
- 是否允许重新开放为 `GAP-BE-PROJ-02`，未确认前不得实现隐式 reopen。

#### `BE-PROJ-006` 我的项目列表（GAP-PROJ-03）

- 返回当前用户拥有的 `DRAFT/PUBLISHED/CLOSED` 项目；
- 不复用只能返回公开项目的大厅语义；
- 提供稳定分页和状态筛选；
- 路径和 DTO 必须在实现前新增到 API 契约。

### 7.5 发现与检索

#### `BE-DISC-001` 项目大厅（API-DISC-01 / DISC-001）

- 只返回允许公开且状态为 `PUBLISHED` 的项目；
- 支持方向、赛事、技能、阶段和允许状态筛选；
- 至少支持最新发布时间稳定排序；
- 对被拉黑关系、内容下架和数据可见性进行服务端过滤；
- 使用游标分页，列表字段最小化；
- 搜索失败时可降级为基础 MySQL 筛选，不返回伪造结果。

#### `BE-DISC-002` 人才大厅（API-DISC-02 / DISC-002）

- 只返回主动公开、账号状态正常的名片；
- 支持技能、方向、合作偏好和可投入时间筛选；
- 双方拉黑后互不出现在可联系结果；
- 不返回联系方式、微信身份和非公开经历；
- 防止无上限分页和批量抓取。

Guest 是否允许浏览公开摘要属于 `IA-GAP-01`，必须在发现模块实现前由角色 A 决定、角色 B 完成隐私评审。

### 7.6 匹配与推荐事件

#### `BE-MATCH-001` 项目候选成员（API-MATCH-01 / MATCH-001/002）

- 只有项目 owner 或明确允许的项目管理者可以请求；
- 先过滤公开状态、账号状态、拉黑、项目/岗位状态、容量和硬约束；
- 再按版本化规则计算技能、方向、时间、专业和经历因素；
- 返回候选 ID、分数、置信度、引擎版本、因素和缺失信息；
- 不暴露非公开特征和治理原因。

#### `BE-MATCH-002` 用户候选项目（API-MATCH-02 / MATCH-001/002）

- 只为当前用户计算；
- 过滤草稿、关闭、隐藏、拉黑和满员岗位；
- 与候选成员方向使用兼容的规则和解释代码；
- 相同规则版本和输入得到稳定结果；
- 冷启动或资料不足时明确返回缺失信息，不虚构高匹配。

#### `BE-MATCH-003` 推荐曝光（API-MATCH-03 / MATCH-003）

- 匹配响应签发不可伪造的 `recommendationRequestId`；
- 只接受该用户此前获得的候选和合法展示位置；
- 曝光按请求、用户和候选幂等去重；
- 限制可接受时间窗口，具体时长 `TBD`；
- 不接受客户端直接声明“成功组队”；
- 详情、联系方式交换、邀请和接受结果由对应业务接口在服务端关联生成。

#### `BE-MATCH-004` P1 轻量模型重排（MATCH-004）

- 只重排已经通过规则硬约束的候选；
- 特征、标签、数据窗口、代码和模型版本可追溯；
- 模型异常、低置信度、schema 不兼容或开关关闭时回退规则结果；
- 模型不能使用禁止的敏感/代理特征；
- 未通过离线、影子、公平性和回滚评审前不得启用生产流量。

### 7.7 联系方式交换

#### `BE-CONTACT-001` 私有联系名片（API-CONTACT-CARD-01/02 / CONTACT-001）

- 只允许本人读取和更新微信号、QQ、邮箱中的至少一种，不接收手机号；
- 联系名片独立于公开能力名片，默认私有，不进入公开列表、匹配响应、日志或推荐数据；
- 更新使用 `version` 乐观锁，响应只返回本人当前服务端快照。

#### `BE-CONTACT-002` 创建和列出交换申请（API-CONTACT-REQ-01/02 / CONTACT-001）

- 客户端只提交 `projectId` 和 `roleId`；recipient 必须由服务端根据项目 owner 派生；
- 创建时检查申请人的联系名片、项目/岗位状态与容量、owner/成员关系和双向拉黑；
- requester 与 recipient 只能在自己的发出/收到列表读取最小摘要；除 `ACCEPTED` 外不得返回对方联系方式；
- 同一 requester、project、role 的待处理申请唯一，重复创建返回原确定结果。

#### `BE-CONTACT-003` 接受、拒绝和取消（API-CONTACT-REQ-03/04/05 / CONTACT-001）

- recipient 只能接受或拒绝自己的 `PENDING` 请求，requester 只能取消自己发出的 `PENDING` 请求；
- 接受时重新检查双方联系名片、双向拉黑和项目/岗位关系，再原子转换为 `ACCEPTED`；
- 只有 `ACCEPTED` 为双方授予读取对方当前联系名片的权限；联系方式值不复制到请求表；
- 重复同终态动作返回原结果，冲突终态返回稳定错误。

#### 历史会话兼容（Deprecated）

`BE-CONV-001/002` 与 `BE-MSG-001/002` 曾按 `MSG-001` 实现双人文本会话。角色 A 已确认 P0 不做聊天，由 `CONTACT-001` 替代；历史接口只保留参与者授权、拉黑、分页和日志脱敏等兼容/安全约束，不进入 P0 页面和发布验收，也不得继续扩展聊天能力。

### 7.8 邀请和组队

#### `BE-TEAM-001` 创建邀请（API-TEAM-01 / TEAM-001）

- 只有项目 owner 可以针对自己的开放岗位邀请用户；
- 验证项目发布状态、岗位开放和容量、邀请对象状态及拉黑关系；
- 防止同一项目/岗位/用户存在无意义的重复待处理邀请；
- 记录创建时间、过期时间和幂等信息。

#### `BE-TEAM-002` 接受邀请（API-TEAM-02 / TEAM-001）

必须在单一事务中：

1. 锁定或以等效并发方式读取邀请和岗位；
2. 确认当前用户是 invitee；
3. 确认邀请为 `PENDING` 且未过期；
4. 确认项目为 `PUBLISHED`、岗位为 `OPEN` 且有容量；
5. 确认不存在有效重复成员；
6. 创建成员关系；
7. 更新邀请状态为 `ACCEPTED`；
8. 记录推荐结果和审计事件。

重复接受必须返回已确定的业务结果，不产生第二条成员关系。并发接受不能让岗位超额。

#### `BE-TEAM-003` 拒绝邀请（API-TEAM-03 / TEAM-001）

- 只有 invitee 可以拒绝自己的 `PENDING` 邀请；
- 重复拒绝不产生额外副作用；
- 已接受、过期或取消的邀请不能转为拒绝；
- 拒绝原因若未来收集，默认不进入推荐特征。

#### `BE-TEAM-004` 邀请列表（API-TEAM-04 / TEAM-001）

- inviter 和 invitee 可分别按 `SENT|RECEIVED` 查看自己的邀请；其他用户列表不得包含该记录；
- 返回项目、岗位、对方昵称、状态、创建/过期/响应时间等最小摘要，不返回联系方式或非公开名片；
- 使用稳定游标分页；读取到已过期的 `PENDING` 邀请时转换为 `EXPIRED` 并释放待处理唯一键。

### 7.9 举报、拉黑与内容治理

#### `BE-SAFE-001` 提交举报（API-SAFE-01 / SAFE-001）

- 允许用户举报合法的用户、项目或消息目标；
- 校验原因和补充说明，不向无权角色公开举报正文；
- 创建待处理举报并记录 request ID；
- 防止举报接口被批量滥用；
- 管理员处理动作必须进入独立审计。

#### `BE-SAFE-002` 拉黑（API-SAFE-02 / SAFE-001）

- 当前用户只能创建自己的拉黑关系；
- 禁止拉黑自己，组合关系唯一；
- 重复拉黑保持幂等；
- 立即阻止双方的新消息、新邀请和可联系发现结果；
- 拉黑原因不得暴露给被拉黑者或进入推荐特征。

#### `BE-SAFE-003` 取消拉黑（API-SAFE-03 / SAFE-001）

- 当前用户只能取消自己创建的拉黑关系；
- 不存在关系时采用明确且幂等的契约；
- 取消拉黑不自动恢复历史邀请、消息发送或成员关系。

#### `BE-SAFE-004` 内容状态与管理处理（SAFE-002）

- 名片、项目和消息支持正常、隐藏/下架、删除等受控状态；
- 管理权限独立分配，不复用普通用户接口；
- 处理动作、原因、操作者、资源和时间进入审计；
- 管理 API 尚未进入公共契约，属于 `GAP-BE-SAFE-01`，上线治理前必须补齐。

## 8. 数据需求

### 8.1 核心实体

| 模块 | 实体 |
| --- | --- |
| 账号 | User、平台会话/撤销记录、注销请求 |
| 名片 | Profile、Skill、ProfileSkill、Experience、Availability |
| 项目 | Project、ProjectRole、ProjectRoleSkill、ProjectMember |
| 匹配 | MatchSnapshot、RecommendationImpression、RecommendationOutcome、ModelVersion |
| 联系 | ContactCard、ContactMethod、ContactExchangeRequest；历史 Conversation/Message 仅作兼容 |
| 组队 | Invitation、ProjectMember |
| 治理 | Block、Report、AuditEvent |

联系名片、交换申请、历史会话、邀请、注销请求和相关唯一键均已在任务堆叠分支形成物理实现；合入 `main` 前仍须完成跨角色契约、隐私和迁移评审。

### 8.2 数据约束

- 微信身份唯一且永不公开；
- 一个用户一个当前名片；
- 技能规范名唯一，关联组合唯一；
- 项目 owner、岗位和成员通过外键或等效约束保持引用完整性；
- `headcount > 0`；
- 有效成员组合唯一；
- 联系名片按用户唯一；同一 requester/project/role 只有一条有效待处理交换申请；
- 历史会话参与者组合唯一；
- 拉黑组合唯一且不能指向自己；
- 推荐曝光可幂等去重；
- 所有业务实体包含统一创建/更新时间，适用资源包含 `version`；
- 所有时间按 UTC 存储；
- 业务状态使用受控枚举，不能用任意字符串驱动状态机。

### 8.3 状态机

```text
Project: DRAFT -> PUBLISHED -> CLOSED
Invitation: PENDING -> ACCEPTED | REJECTED | EXPIRED | CANCELLED
User: ACTIVE -> SUSPENDED | DELETION_PENDING -> DELETED/ANONYMIZED
```

额外规则：

- 不实现未确认的逆向状态转换；
- 状态转换必须由领域服务统一执行，不允许任意表字段更新；
- 重要转换记录 actor、resource、request ID 和时间；
- 失败事务不能留下部分状态。

### 8.4 迁移与索引

- 所有 schema 变化使用版本化迁移；
- 迁移测试覆盖空库和已有数据升级；
- 生产禁止手工执行未版本化 DDL；
- 破坏性修改采用新增、回填/双写、切读、删除的分阶段方案；
- 索引根据真实查询和 `EXPLAIN` 验证，不盲目增加；
- 首版重点评估微信身份、项目大厅、岗位、技能、联系方式交换列表、邀请列表、拉黑和举报查询。

### 8.5 隐私与保留

数据分为 Public、Internal、Sensitive 和 Secret。每个字段必须记录用途、必需性、可见范围和保留期限。联系方式、历史消息、举报、审计、已关闭项目、注销用户和训练派生数据的具体保留期限为 `GAP-BE-PRIV-01`，上线前必须由双方结合适用要求确认。

## 9. 安全需求

| ID | 要求 | 验收 |
| --- | --- | --- |
| `BE-SEC-001` | 所有受保护接口认证 | 无效/撤销/过期凭证全部拒绝 |
| `BE-SEC-002` | 资源级授权和 IDOR 防护 | 用户不能读取或修改越权资源 |
| `BE-SEC-003` | 输入与内容校验 | 类型、长度、枚举、状态和关系均服务端校验 |
| `BE-SEC-004` | 密钥管理 | 密钥只通过环境/密钥服务注入，不进仓库和日志 |
| `BE-SEC-005` | 日志脱敏 | token、微信凭证、密钥、联系方式值和历史私信正文无日志命中 |
| `BE-SEC-006` | 接口限流 | 登录、搜索、联系方式交换、邀请、举报和 AI 分别受控 |
| `BE-SEC-007` | 审计 | 管理、高风险和数据权利操作可追溯 |
| `BE-SEC-008` | 拉黑一致性 | 发现、匹配、联系方式交换、历史消息和邀请均不能绕过拉黑 |
| `BE-SEC-009` | 依赖与配置安全 | 无未处理高危依赖、生产无调试配置 |
| `BE-SEC-010` | 数据保护 | TLS、数据库/备份访问控制和恢复验证可执行 |

资源不存在和无权访问的响应策略必须避免泄露敏感资源是否存在。管理员权限必须独立建模并最小授权，不能只依赖前端入口隐藏。

## 10. 外部服务与降级

### 10.1 微信登录接口

- 设置连接和读取超时、受控重试与限流；
- 不复用一次性凭证；
- 失败不创建半完成会话；
- 不记录完整请求和响应中的敏感字段；
- stub 覆盖成功、无效凭证、超时、限流和异常响应。

### 10.2 生成式 AI（P1 可选）

- 所有调用经过 AI Gateway；
- 仅发送任务所需的最小字段；
- 设置预算、频率、超时、功能开关和模板降级；
- 输出做 schema、长度、事实和内容校验；
- AI 不写入认证状态、匹配分数、成员关系或处罚结果；
- AI 不可用时，P0 登录、发布、匹配、联系方式交换和组队仍可用。

### 10.3 推荐模型（P1）

- 规则层始终先执行；
- 模型加载、schema、超时和输出异常立即回退规则；
- API 结构不因回退变化；
- 记录 `engineType`、`engineVersion` 和 `modelVersion`；
- 模型文件来源、校验和、访问权限和回滚版本可审计。

## 11. 非功能需求

### 11.1 可靠性

- 核心写操作明确事务边界；
- 可重复请求具有幂等或状态保护；
- 外部依赖失败不产生伪成功和半完成业务数据；
- 数据库迁移、备份和恢复在 staging 验证；
- 发布支持停止和回滚/安全前滚。

### 11.2 性能

- 不在缺少真实接口和负载基线时虚构 QPS、P95 或数据规模；
- 完成首条纵向切片后记录登录、名片、项目列表、联系方式交换和匹配基线；
- 分页上限、连接池、超时、限流和慢查询阈值通过性能任务确认；
- 优先使用 MySQL 索引和查询优化，只有证据证明不足时新增基础设施。

### 11.3 可观测性

- 请求 ID 覆盖入口、数据库、外部调用和错误响应；
- 结构化日志记录模块、动作、资源 ID、结果、错误码、耗时和环境；
- 关键指标至少覆盖健康、错误率、延迟、登录失败、发布失败、匹配空结果、联系申请失败和邀请失败；
- 告警阈值在 staging 基线后确认；
- 审计日志与普通调试日志分开治理。

### 11.4 兼容性

- 新增可选响应字段通常向后兼容；
- 删除、重命名、改类型、改变含义或收紧枚举属于破坏性变更；
- 破坏性变更必须更新 API 版本、OpenAPI、前后端任务和迁移/ADR；
- 实现必须通过 OpenAPI 契约测试；
- mock 必须从契约生成或受契约测试约束。

### 11.5 可维护性

- 模块间通过应用服务和领域对象协作，不随意跨模块访问内部表；
- 业务规则、状态机和权限策略具有单元测试；
- 配置按环境分离且有安全默认值；
- 依赖版本锁定，升级使用独立任务；
- 真实安装、启动、迁移、seed、测试、lint、类型检查和构建命令进入开发指南。

## 12. 环境、配置与部署

| 环境 | 用途 | 数据规则 |
| --- | --- | --- |
| local | 开发和单元测试 | 构造/匿名数据，非生产登录替代方案 |
| test | 自动化集成和契约测试 | 可重复创建和清理，不使用生产数据 |
| staging | 前后端验收和发布演练 | 独立账号/数据库，配置接近生产 |
| production | 真实用户 | 最小权限、备份、监控、审计和 TLS |

配置要求：

- 仓库只提交 `.env.example`，包含变量名和安全占位；
- 微信密钥、平台签名密钥、数据库凭证和 AI key 仅在服务端运行环境；
- 每个配置说明用途、是否必需、默认行为和安全等级；
- CORS/允许域名、微信配置、数据库和对象存储必须指向正确环境；
- staging/production 的部署拓扑、计算、数据库、密钥、日志和告警产品组合通过单独部署 ADR 确认。

## 13. 测试与验收

### 13.1 测试层级

| 层级 | 后端要求 |
| --- | --- |
| 单元测试 | 校验、权限、状态机、错误映射、匹配规则 |
| 数据库集成 | 真实 MySQL 约束、事务、锁、查询和迁移 |
| API 集成 | 路由、DTO、认证、错误、分页和幂等 |
| 契约测试 | OpenAPI 与实际请求/响应/错误码一致 |
| E2E | 登录、名片、发布、匹配、联系方式交换、邀请接受 |
| 安全测试 | IDOR、伪造 owner、拉黑绕过、限流和敏感日志 |
| 发布烟测 | 健康、迁移、主路径、外部依赖降级和回滚 |

### 13.2 每个资源接口的最低用例

- 未认证；
- 资源所有者/合法参与者；
- 非所有者/非参与者；
- 资源不存在或不可见；
- 字段校验失败；
- 非法状态转换；
- 重复请求；
- 版本或数据库并发冲突；
- 外部服务失败（适用时）；
- 响应和日志敏感信息检查。

## 17. 后端完成定义

某项后端功能只有同时满足以下条件才算完成：

- 引用并满足对应产品需求、后端需求和 API ID；
- OpenAPI、实现、错误码和前端 mock 一致；
- 数据迁移、约束、事务和回滚/修复策略已验证；
- 未认证、越权、非法状态、重复请求和并发场景通过；
- 日志、响应和测试数据无密钥或敏感信息泄漏；
- 单元、集成、契约、安全和适用 E2E 实际通过；
- 开发/运行文档、任务状态和评审记录同步；
- 角色 A 完成产品与契约验收，角色 B 完成后端、数据、安全和部署验收；
- 剩余风险和未运行检查明确记录。

本文从 `Proposed` 转为 `Confirmed` 前，需要角色 A 确认产品行为与前端契约，角色 B 确认技术可行性、数据、安全和运维边界。
