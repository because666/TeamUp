# 自训练轻量推荐模型

> Status: Proposed<br>
> Owner: 角色 A（目标与特征）/ 角色 B（数据与服务）<br>
> Decision: [ADR-0002](../decisions/ADR-0002-mvp-ai-scope.md)<br>
> Last Updated: 2026-08-10

## 1. 目标与边界

TeamUp 将使用自己的平台数据训练轻量机器学习排序模型，提高“候选项目/成员最终形成有效合作”的概率。模型不负责生成候选、鉴权或安全治理，只重排已经通过规则层检查的候选。

```text
公开且合法的数据
      |
硬约束与候选生成（规则，始终启用）
      |
规则特征计算
      |
P0: 规则排序 ----------+
      |                  |
曝光与结果事件          | fallback
      |                  |
离线数据集 -> 小模型 -> P1 模型重排
                         |
                  结构化解释与版本
```

通用大模型不参与最终匹配分数。个人简介、缺口建议和文案润色若以后接入，是独立的生成式功能。

## 2. 为什么先规则、后训练

新平台没有足够的曝光和真实组队结果，直接训练只会学习人工构造标签、位置偏差或随机噪声。P0 规则系统同时解决三个问题：

- 提供可上线、可解释的冷启动推荐；
- 产生稳定的候选和版本，便于比较后续模型；
- 记录曝光到组队的完整反馈，为训练建立可信分母和标签。

禁止为了展示“自研模型”使用少量手工样本训练后直接上线。

## 3. 推荐流水线

### 3.1 候选生成

使用 [MATCHING.md](MATCHING.md) 的硬约束过滤：公开状态、项目/岗位状态、容量、拉黑、必需技能、时间和合作偏好。此层不由模型替代。

### 3.2 特征计算

首批特征只来自用户主动提供或业务过程产生的结构化数据：

| Feature Group | 示例 | 约束 |
| --- | --- | --- |
| Skill | 必需技能覆盖率、加分技能重合 | 不根据简介自由文本猜测未声明技能 |
| Direction | 用户意向与项目方向重合 | 使用受控分类 |
| Availability | 时间段重合、每周投入差异 | 缺失单独编码，不等同于零 |
| Experience | 相关类型数量、认证状态 | 自述和认证分开 |
| Preference | 队长/队员、合作场景 | 用户可修改 |
| Context | 项目阶段、开放岗位数、候选方向 | 不使用无关个人属性 |
| Quality | 资料完整度、数据更新时间 | 只表达置信度，不评价个人能力 |

禁止特征：学校层级排名、性别、民族、家庭背景、联系方式、微信身份、私信正文、举报原文、拉黑原因和无关设备标识。学校/专业名称是否作为特征需另行公平性评审，默认只使用用户选择的专业方向相似度。

### 3.3 排序

- P0：使用版本化规则 `match-v0.x`；
- P1：模型 `rank-v1.x` 产出重排分数；
- 最终结果同时返回规则/模型版本、置信度和安全的结构化解释因素；
- 模型只对规则候选重排，结果为空或失败时返回规则结果。

## 4. 事件与标签

必须先记录曝光，才能解释“用户没有操作”：

| Event | 信号强度 | 用法 |
| --- | --- | --- |
| recommendation_impression | 分母 | 记录实际展示位置和引擎版本，不是正负标签 |
| project/profile_viewed | 弱正向 | 表示进一步了解，受位置和标题影响 |
| conversation_started | 中等正向 | 表示有沟通意愿 |
| invitation_sent | 中等正向 | 项目方明确意愿 |
| invitation_accepted | 强正向 | 双方形成明确意向 |
| team_join_confirmed | 最强正向 | 核心业务结果 |
| invitation_rejected | 显式负向 | 需要结合原因与观察窗口，原因不直接作为特征 |
| project_closed/role_filled | 截断信号 | 之后的沉默不能当作负样本 |

未曝光候选不是负样本；没有点击可能是位置偏差或用户未完整浏览；邀请过期也不能自动等同于不匹配。标签生成规则必须版本化。

## 5. 数据集构建

- 以推荐请求/曝光为基本样本，关联观察窗口内的业务结果；
- 使用时间切分训练、验证和测试，避免未来数据泄漏；
- 同一用户/项目的高度相似事件要去重，防止活跃用户支配样本；
- 训练时记录候选位置和规则版本，用于分析展示偏差；
- 类别不平衡使用权重或采样处理，但保留真实分布的最终测试集；
- 特征提取代码在线上线共用同一 schema 版本，避免训练/服务偏差；
- 用户注销、撤回同意或数据到期时，按政策处理原始与派生训练数据。

## 6. 模型选择顺序

1. **规则基线**：`match-v0.x`，任何模型必须超过它才有上线价值。
2. **逻辑回归**：验证标签、特征方向和完整流水线，易解释、易部署。
3. **GBDT**：只有逻辑回归无法表达的非线性关系有稳定证据时评估，例如 LightGBM/XGBoost。
4. **Learning-to-rank**：候选组和有效反馈足够后评估 pairwise/listwise 排序。

首轮不采用深度神经网络、在线实时训练或向量数据库。模型库和运行方式需在后端技术栈确定后通过依赖评审。

## 7. 评估

### 7.1 离线

- 排序：`NDCG@K`、`MRR`、`Recall@K`；
- 概率（若输出）：log loss、Brier score 和校准曲线；
- 业务代理：邀请接受/组队确认的排序提升；
- 稳定性：按时间、冷启动、资料完整度和项目类型分组；
- 公平性：检查允许使用的群体维度上是否存在无法解释的系统性差异。

不要只看 accuracy，也不要用训练集结果作为上线证据。

### 7.2 在线

上线顺序：离线通过 -> staging 回放 -> 生产影子模式 -> 小流量实验 -> 扩大流量。

在线主指标应接近真实合作结果，例如有效会话率、邀请接受率和组队确认率；点击率只能作为诊断指标。实验同时监控举报/拉黑率、延迟、空结果率和规则降级率。

具体样本量和提升门槛不能现在猜定，应在获得首批真实分布后由一次模型上线评审记录确认。

## 8. 解释与用户体验

- 不向用户展示模型内部术语或“你能力不足”等评价；
- 将主要允许特征贡献映射为受控 reason code，例如技能重合、方向一致、时间适配；
- 不展示可能推断隐私、拉黑或治理状态的贡献；
- 分数用于排序，不承诺成功概率；界面应同时显示可理解的匹配点与待确认项；
- 生成式 AI 若润色解释，只能使用匹配服务返回的结构化因素。

## 9. 模型登记与发布

每个模型版本至少登记：

- 代码提交、训练数据窗口和标签版本；
- 特征 schema、算法、超参数和随机种子；
- 离线指标、分组指标和与规则基线比较；
- 模型文件校验和、依赖版本和训练负责人；
- 状态：candidate、shadow、canary、active、retired；
- 回滚目标和不兼容条件。

发布记录使用 [MODEL_RELEASE_TEMPLATE.md](../status/templates/MODEL_RELEASE_TEMPLATE.md)。

模型文件不得随意提交到 Git。正式存储位置、签名/校验和访问权限由部署 ADR 决定。优先使用可校验的安全模型格式；不得加载来源不明的 pickle/joblib 等可执行反序列化产物。

## 10. 推理与回退

- 首选后端进程内推理以降低首版运维复杂度；只有语言/依赖或扩展性证明确有需要时拆模型服务；
- 设置推理超时、模型加载校验和最大候选数；
- 特征 schema 不匹配、模型缺失、异常输出、延迟超限或功能开关关闭时回退规则排序；
- 降级不改变 API 结构，通过 `engineType`、版本和内部监控体现；
- 模型发布不覆盖旧版本，至少保留一个已验证回滚版本。

## 11. 上线检查

- [ ] 训练数据字段和合法用途已评审
- [ ] 曝光、标签、特征和模型版本可追溯
- [ ] 无训练/测试时间泄漏
- [ ] 超过规则基线且分组结果无不可接受退化
- [ ] 影子模式验证线上特征一致
- [ ] 冷启动、错误、超时和回滚测试通过
- [ ] 规则硬约束在模型前后均不可绕过
- [ ] 角色 A 完成产品效果验收，角色 B 完成数据、安全和运行验收
