# ADR-0002: 推荐系统与生成式 AI 边界

> Status: Accepted<br>
> Decision Owner: 角色 A<br>
> Technical Reviewer: 角色 B（实现前评审）<br>
> Accepted Date: 2026-08-10

## Context

原始产品 PRD 将完整 AI 匹配、简介优化和团队缺口分析放到 V2.0，但团队分工说明书将这些能力列为 MVP。项目需要明确“智能匹配”究竟来自通用大模型、自己训练的模型还是确定性算法。

新平台在冷启动阶段没有足够的真实曝光、沟通、邀请和组队结果。此时直接训练模型只能依赖人工标签或极小样本，难以证明真实推荐价值。

## Decision Drivers

- 推荐效果必须可测量、可解释并能回退；
- 平台应形成自己的数据和模型能力，而不是把通用大模型包装成推荐系统；
- 冷启动时也要提供稳定、可用的匹配；
- 训练数据必须合规、最小化并避免位置偏差和数据泄漏；
- 两人团队的开发、部署和运维复杂度可控。

## Decision

采用“规则算法 P0 + 自训练轻量排序模型 P1”的分阶段路线：

1. P0 使用版本化规则算法完成硬约束过滤、候选排序、解释和冷启动。
2. P0 同时记录推荐曝光、详情、沟通、邀请、接受和组队确认等合规事件。
3. 数据质量通过评审后，P1 使用平台自身数据离线训练轻量排序模型。
4. 首个模型以逻辑回归作为可解释基线；只有数据证明需要时再评估 GBDT 或 learning-to-rank。
5. 模型只重排已通过规则硬约束的候选，不能绕过权限、拉黑、岗位容量、必需条件或隐私规则。
6. 模型须经过时间切分离线评估、影子运行和小流量验证；异常、冷启动或低置信度时回退规则算法。
7. 通用大模型不参与最终匹配分数。个人简介、团队缺口建议和解释润色属于独立、可选的生成式功能。

具体设计见 [MATCHING.md](../architecture/MATCHING.md) 和 [ML_RECOMMENDER.md](../architecture/ML_RECOMMENDER.md)。

## Model Activation Gate

不提前虚构固定样本量。P1 训练和上线前必须由角色 A、B 共同评审：

- 是否有可信曝光分母和足够的强结果标签；
- 是否存在训练/测试时间泄漏、位置偏差或重复样本；
- 是否稳定超过规则基线；
- 分组效果、公平性、延迟和降级是否可接受；
- 模型、特征、标签和数据窗口是否可追溯并可回滚。

评审结论进入独立模型发布记录，不只保留在实验笔记或聊天中。

## Rejected Alternatives

### 通用大模型直接打匹配分

拒绝原因：结果不稳定、解释和评估困难、隐私及成本风险高，也无法形成可信的自有推荐能力。

### 冷启动阶段直接训练小模型上线

拒绝原因：缺少真实分母和结果标签，容易学习人工偏好、位置偏差和噪声。

### 长期只用固定规则

不作为长期终点。规则适合冷启动和兜底，但在有足够真实数据后应通过受控实验验证轻量模型是否能带来稳定提升。

### 首版使用深度模型或向量数据库

拒绝原因：当前数据量和团队规模无法证明复杂度收益，增加训练、部署、监控和解释成本。

## Consequences

- P0 必须把推荐事件、规则版本和结果标签纳入数据与测试设计；
- 规则算法不会因模型上线而删除，始终承担安全约束和降级；
- 需要建立离线训练、模型登记、影子模式和回滚能力；
- 推荐模型所需库、模型格式和推理方式在后端框架确定后单独评审；
- 生成式 AI 可以延期或关闭，不影响推荐主链路。

## Review Triggers

出现以下情况时复审本 ADR：训练数据长期不足、模型未能超过规则基线、合规要求变化、推理成本/延迟不可接受，或产品目标从组队成功转向其他主要结果。
