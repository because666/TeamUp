# 双人 Git 与文件同步工作流

> Status: Proposed<br>
> Owner: 角色 A / 角色 B<br>
> Last Updated: 2026-08-10

## 1. 核心规则

- `main` 是可集成真值，不作为两人日常并行开发分支；
- 一项任务一个负责人、一个分支、一个任务状态文件；
- 两人不得同时在同一功能分支让 AI 修改文件；
- 跨前后端功能先稳定契约，再并行实现；
- AI 不自动 commit、push、merge 或部署，除非当前用户明确要求；
- QQ 只负责通知，任务状态、评审结论和决定以仓库文件为准；
- Pull Request 可选，但另一角色的仓库评审记录不可省略；
- 不用强制推送和历史重写解决协作问题。

## 2. 分支命名

```text
role-a/<type>/<task-id>-<slug>
role-b/<type>/<task-id>-<slug>
```

`type` 使用 `feature`、`fix`、`docs`、`refactor`、`test`、`chore`。任务 ID 使用 `TUP-<number>` 或在正式任务系统启用前使用 `TUP-YYYYMMDD-<short-name>`。

## 3. 开始一天或新任务

先确认工作区：

```bash
git status --short --branch
git fetch --prune origin
```

只有工作区干净时才切回并更新主分支：

```bash
git switch main
git pull --ff-only origin main
git switch -c role-a/feature/TUP-001-example
```

角色 B 将前缀改为 `role-b`。如果 `pull --ff-only` 失败，先检查本地提交，不要改用强制 reset。

随后按 [任务模板](../status/templates/TASK_TEMPLATE.md) 创建 `docs/status/tasks/<TASK-ID>.md`，填写基线提交、范围、依赖和负责人。

## 4. 并行修改规则

| 文件/领域 | 默认主责 | 并行要求 |
| --- | --- | --- |
| 产品、交互、前端、AI 提示与运营 | 角色 A | 涉及接口/隐私时由 B 评审 |
| 后端、数据库、部署、运维、安全 | 角色 B | 涉及产品行为时由 A 评审 |
| API 契约、数据模型、匹配规则 | 双方 | 先建独立契约任务或指定唯一编辑者 |
| `CURRENT.md` | 合并/交接者 | 不写逐步日志 |
| 任务文件 | 对应分支负责人 | 其他分支不修改 |

高冲突文件只能指定一个编辑者。另一方通过评审意见或独立提案文件提供输入，不复制出第二份“最终版”。

## 5. 同步远程变化

提交自己的工作后再同步：

```bash
git fetch --prune origin
git rebase origin/main
```

仅对自己的未共享任务分支 rebase。若分支已被他人基于其工作继续开发，改用 merge 或双方明确协调。遇到冲突：

1. 确认每个冲突块背后的需求和所有者；
2. 优先保留双方有效行为，而不是机械选 ours/theirs；
3. API/数据冲突回到契约和 ADR 判断；
4. 解决后重新运行受影响测试；
5. 在任务文件记录重要冲突和结论。

## 6. 提交、评审与集成

提交格式：

```text
<type>(<scope>): <summary>
```

示例：`feat(profile): add availability preferences`。

任务分支应小而完整，必须包含代码、测试、相关文档和任务状态。请求另一角色评审前，在 `docs/status/reviews/` 建立独立评审文件，明确：

- 需求 ID 与任务 ID；
- 行为、接口、数据和安全影响；
- 实际验证结果；
- 截图/接口样例；
- 风险与回滚方案；
- 需要另一角色重点检查的内容。

评审人必须在该文件中给出阻塞问题、非阻塞问题、相关 ADR 结论和 `Approved` / `Changes Requested` 总结。也可以通过 QQ 发送可原样落盘的完整 Markdown，由任务负责人据实写入。没有明确评审结论不得集成到 `main`。

Pull Request 可按需要使用；使用时引用任务文件和评审文件。不使用 PR 时，远程任务分支、Git 提交和仓库评审文件共同构成可追溯记录。

## 7. 合并顺序

跨角色功能推荐：

1. 合并契约/ADR；
2. 更新双方分支到该契约基线；
3. 合并后端实现和契约测试；
4. 合并前端实现和联调测试；
5. 合并状态快照与发布准备。

若前后端必须在同一评审批次集成，指定一位集成负责人，其他人停止修改高冲突文件直到集成完成。

## 8. 交接

需要由另一角色继续时，不只发送聊天消息。必须：

1. 更新任务文件当前状态和最后提交；
2. 新建或填写 [交接模板](../status/templates/HANDOFF_TEMPLATE.md)；
3. 列出已完成、未完成、验证结果、接口变化、已知问题和下一步；
4. 推送远程分支后通过 QQ 通知接收方；QQ 不承载交接正文；
5. 接收方从远程分支和记录恢复工作，不依赖发送方本地未提交文件。

## 9. 异常处理

- 工作区有不明改动：停止覆盖，联系所有者；
- 意外提交密钥：立即停止传播并轮换密钥，仅删除 Git 文件不够；
- 主分支构建失败：暂停新合并，建立修复任务；
- 文档和实现冲突：记录差异，由对应产品/技术负责人确认；
- 无法同步远程：任务文件标记基线可能过期，恢复网络后先比较再继续。
