## 1. 目标与适用范围

本文规定角色 A（产品、前端）与角色 B（后端、数据库、安全）如何基于同一份契约并行开发、联调和交付。它不重复定义业务字段；接口字段以 [API 契约](../architecture/API_CONTRACT.md) 和未来的 OpenAPI 文件为唯一真值，数据约束以 [数据模型](../architecture/DATA_MODEL.md) 为准。

当前前后端工程尚未初始化，框架版本、环境变量名和可执行命令仍为 `TBD`。这些内容只有在工程初始化并实际验证后，才能写入 [开发指南](DEVELOPMENT.md)。

## 4. 首条 P0 纵向切片

首轮联调按“微信登录 -> 能力名片 -> 创建并发布项目”推进。先闭环一条路径，再扩展大厅、匹配、消息和邀请。

| 顺序 | 用户行为 | API ID | Method / Path | 前端交付 | 后端交付 |
| --- | --- | --- | --- | --- | --- |
| 1 | 微信登录 | API-AUTH-01 | `POST /api/v1/auth/wechat/login` | 获取一次性 `code`、提交同意版本、保存平台会话 | 换取微信身份、签发平台会话、限流和脱敏日志 |
| 2 | 读取名片 | API-PROF-01 | `GET /api/v1/me/profile` | loading、未完善、成功、401 状态 | 仅返回当前用户完整名片和 `version` |
| 3 | 编辑名片 | API-PROF-02 | `PUT /api/v1/me/profile` | 表单校验、保存中、防重复提交、冲突提示 | 服务端校验、所有权判断、乐观锁和稳定错误码 |
| 4 | 创建草稿 | API-PROJ-01 | `POST /api/v1/projects` | 项目/岗位表单、草稿成功状态 | 创建 owner 为当前用户的草稿，忽略客户端 owner 字段 |
| 5 | 修改草稿 | API-PROJ-03 | `PATCH /api/v1/projects/{projectId}` | 携带版本、处理 `409` | 校验 owner、状态和 `version`，原子更新 |
| 6 | 发布项目 | API-PROJ-04 | `POST /api/v1/projects/{projectId}/publish` | 发布中、校验失败、发布成功页 | 检查字段完整和至少一个开放岗位，保证重复请求安全 |
| 7 | 查看项目 | API-PROJ-02 | `GET /api/v1/projects/{projectId}` | 详情、无权限/不存在、重试 | 按状态、身份和拉黑关系过滤可见字段 |

每个接口进入实现前必须补齐请求 DTO、响应 DTO、状态码、稳定错误码、权限条件和至少一组示例。以上路径已存在于契约草案，但具体 DTO 仍需双方确认。

## 5. 标准协作流程

### 5.1 契约准备

1. 角色 A 用 PRD ID 和页面场景描述需要的数据，不直接从页面结构推导数据库字段。
2. 角色 B 给出请求、响应、错误码、权限、幂等和分页方案，并更新 OpenAPI/契约。
3. 双方确认字段含义、必填性、空值、枚举、时间格式、可见性和兼容性。
4. 契约评审通过后记录基线提交 SHA。前后端任务都引用该 SHA 和 API ID。

契约冻结的含义是“本轮实现按该版本进行”，不是永不变化。冻结后发现缺口，按第 9 节变更，不在各自代码里静默补字段。

### 5.2 并行实现

角色 A：

- 从 OpenAPI 生成类型/客户端；工具链未确定前，mock DTO 必须逐字段对应契约；
- 所有请求经过统一适配层，页面不直接拼 URL、解析 token 或判断服务端权限；
- 实现 loading、empty、error、success、retry、401、403、409 和重复提交状态；
- mock 与真实后端用配置切换，生产构建禁止启用 mock。

角色 B：

- 先实现 OpenAPI、统一响应结构、请求 ID、认证中间件和错误映射；
- 服务端执行字段校验、资源级授权、状态机、幂等和事务，不信任客户端的 `ownerId`；
- 提供构造数据、数据库迁移和可重复的 test/seed 方式；
- 接口测试覆盖正常、未认证、越权、校验失败、版本冲突和重复请求。

### 5.3 本地联调

工程初始化后，角色 B 在开发指南登记经验证的后端启动、迁移、seed 和测试命令；角色 A 登记前端启动、类型检查、测试和构建命令。首次联调按以下顺序：

1. 后端健康检查、数据库迁移和构造数据通过；
2. 前端关闭 mock，基础 URL 指向本地或 test 环境；
3. 先验证 401 和登录，再验证名片读写，最后验证项目草稿和发布；
4. 双方以相同 `requestId` 对齐前端错误、HTTP 响应和后端日志；
5. 记录通过场景、失败场景、环境、契约 SHA 和未决问题。

微信一次性登录凭证不能伪造进生产接口。local/test 如何替代登录必须由角色 B 设计成仅非生产可用的安全方案，并经过角色 A 评审；不得提交真实微信凭证。

### 5.4 staging 验收

- 角色 B 提供 staging 地址、部署提交 SHA、迁移版本和健康状态，不通过 QQ/文档提交凭证；
- 角色 A 使用真实小程序测试配置执行 P0 用户流程和页面状态验收；
- 角色 B 同时检查日志脱敏、资源级授权、幂等、事务和数据库结果；
- 缺陷使用独立 Task ID，写清环境、账号类型、请求 ID、复现步骤、期望和实际结果；
- P0 阻塞问题清零后，双方在评审文件给出结论，再按既定顺序集成。

## 6. HTTP 与客户端适配约定

所有接口共同遵守：

- 基础路径为 `/api/v1`，生产仅使用 HTTPS；
- 使用 `application/json; charset=utf-8`；
- 时间为 ISO 8601 UTC，ID 按不透明字符串处理；
- 受保护接口发送 `Authorization: Bearer <token>`；
- 客户端逻辑只依赖 `error.code`，不解析 `message`；
- `401` 触发会话失效流程，`403` 展示无权限，`409` 进入版本冲突/刷新流程；
- 写操作需要重复提交保护时发送 `Idempotency-Key`，具体适用接口在 OpenAPI 标注；
- 客户端忽略未知的可选响应字段，但未知枚举不得自动当作成功状态。

成功响应基线：

```json
{
  "data": {},
  "meta": {},
  "requestId": "req_xxx"
}
```

错误响应基线：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "提交内容不符合要求",
    "details": []
  },
  "requestId": "req_xxx"
}
```

前端请求适配层至少统一处理：基础 URL、超时、平台会话、`requestId`、错误映射和一次性的 401 退出流程。不得在网络层自动重试非幂等写操作。

## 7. Mock 与测试数据

Mock 是前端并行开发工具，不是第二份契约。规则如下：

- 优先从 OpenAPI 自动生成 mock；暂时手写时，fixture 名称注明对应 API ID 和契约 SHA；
- 同时准备成功、空数据、401、403、404、409、422/校验错误和服务不可用场景；
- mock 返回统一响应结构和稳定错误码，不返回页面专用的临时字段；
- fixture 只用构造/匿名数据，不包含真实微信标识、联系方式、token 或私信；
- 真实联调通过后保留 mock 作为前端测试夹具，但生产构建必须有检查防止启用；
- 后端 seed 数据覆盖 owner、普通用户、未完善资料用户、项目草稿、已发布项目、版本冲突和越权场景。

## 8. 联调验收矩阵

每个 P0 API 至少记录以下证据：

| 类别 | 必测场景 | 责任人 |
| --- | --- | --- |
| 正常路径 | 合法请求返回契约结构，页面完成预期跳转 | A + B |
| 认证 | 无 token、过期 token、退出后的 token | B 主测，A 验证前端状态 |
| 授权 | 读取/修改他人名片或项目、非 owner 发布项目 | B |
| 校验 | 必填缺失、长度超限、未知枚举、非法状态 | B 返回错误，A 映射提示 |
| 并发 | 旧 `version` 更新、重复发布或重复接受 | B |
| 网络 | 超时、断网、5xx、重试后恢复 | A |
| 隐私 | 响应和日志不出现 token、微信标识、非公开字段 | B，A 复核响应 |
| 兼容 | 新增可选字段不破坏旧前端，未知枚举不误判 | A + B |

不以“页面看起来正常”代替接口测试，也不以“接口返回 200”代替产品验收。

## 9. 契约缺口与变更流程

发现契约缺口时创建稳定 ID：`GAP-<TASK-ID>-NN`，并在任务文件记录：

```text
Gap ID：GAP-TUP-xxx-01
触发页面/API：
当前契约：
期望行为：
兼容性影响：
建议方案：
唯一编辑者：
评审人：
```

处理顺序：

1. 暂停依赖该字段的真实实现，可继续不受影响的工作；
2. 唯一编辑者修改 OpenAPI、`API_CONTRACT.md` 或 `DATA_MODEL.md`；
3. 双方评审兼容性、数据迁移、权限和页面影响；
4. 契约先集成，前后端再更新各自分支；
5. 重新生成类型/mock 并运行契约测试和受影响联调场景。

新增可选响应字段通常兼容；删除、重命名、改类型、改变语义或收紧合法值属于破坏性变更，必须给出版本与迁移方案。禁止仅在 QQ 里确认后直接改代码。

## 10. Fork、分支与交付

`origin` / `upstream` 的名称以双方本地实际配置为准，不假设每个人完全相同。开始任务先执行：

```bash
git remote -v
git status --short --branch
git fetch --prune <共享仓库远程名>
```

角色 A 使用 `role-a/<type>/<task-id>-<slug>`，角色 B 使用 `role-b/<type>/<task-id>-<slug>`。双方各自在自己的 fork/远程任务分支工作，不在同一功能分支并行修改。

推荐集成顺序：

1. 契约/ADR 分支评审并集成；
2. 前后端任务分支更新到同一契约 SHA；
3. 后端实现与接口/契约测试评审并集成；
4. 前端实现与联调证据评审并集成；
5. 集成负责人更新 `CURRENT.md` 和发布准备。

每次交付必须提供：远程分支名、最新提交 SHA、任务文件、评审文件、契约 SHA、实际测试结果、未运行检查和剩余风险。PR 可选，但跨角色评审记录不可省略。AI 未获当前用户明确授权时不得 commit、push、merge 或部署。

## 11. 日常同步与问题定位

建议每天只同步一次可落盘的短状态：

```text
Task / Owner：
Branch / Commit：
Contract SHA：
Completed：
Next：
Blocked / Need review：
Validation：
```

QQ 只用于通知对方查看分支、任务或评审文件。排查接口问题时按以下顺序收集：环境、前端提交、后端提交、契约 SHA、API ID、HTTP 状态、`error.code`、`requestId`、复现步骤。不得在截图或聊天中发送 token、微信 `code`、密钥、数据库连接串或真实个人资料。

## 12. 本轮完成定义

首条 P0 纵向切片只有同时满足以下条件才算联调完成：

- API-AUTH-01、API-PROF-01/02、API-PROJ-01/02/03/04 的 DTO、错误码和权限已确认；
- 前端关闭 mock 后完成登录、名片、项目草稿与发布的正常和失败路径；
- 后端接口、契约、授权、幂等/并发和日志脱敏测试通过；
- staging 使用同一契约版本完成产品验收；
- 任务文件和评审文件记录了真实命令、结果、提交 SHA 和剩余风险；
- 角色 A 完成产品/前端验收，角色 B 完成后端/数据/安全验收。
