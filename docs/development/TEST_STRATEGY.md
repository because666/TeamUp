# TeamUp 测试策略

> Status: Proposed<br>
> Owner: 角色 A / 角色 B<br>
> Last Updated: 2026-08-10

## 1. 原则

- 测试覆盖业务风险，不只追求覆盖率数字；
- 关键规则优先使用快速、确定性的单元测试；
- 前后端通过契约测试防止 DTO 和错误码漂移；
- 登录、发布、匹配、沟通和邀请接受使用集成/E2E 验证；
- AI 测试分离“规则正确性”和“自然语言质量”，不依赖在线模型才能通过主 CI。

## 2. 测试层级

| 层级 | 目标 | 典型内容 |
| --- | --- | --- |
| 单元 | 纯规则和边界 | 校验、状态机、匹配因素、权限策略、错误映射 |
| 组件 | 单个前端组件 | 表单状态、加载/失败/空状态、交互事件 |
| 集成 | 数据库和模块协作 | 事务、唯一约束、邀请幂等、消息权限、迁移 |
| 契约 | 前后端一致 | OpenAPI、请求/响应 schema、错误码、mock 一致性 |
| E2E | 真实用户闭环 | 登录替身、资料、项目、匹配、会话、接受邀请 |
| 安全 | 滥用与越权 | IDOR、伪造 owner、拉黑绕过、敏感日志、限流 |
| 发布烟测 | 环境可用 | 健康检查、主路径、外部依赖降级、回滚验证 |

## 3. P0 必测场景

- 无效/过期微信凭证和会话撤销；
- 用户不能修改他人名片或项目；
- 草稿不出现在大厅，关闭/满员岗位不能接受邀请；
- 重复点击接受邀请只产生一个成员关系；
- 拉黑后消息和邀请均在服务端被拒绝；
- 私信只对参与者可见；
- 匹配对相同输入稳定，硬约束、缺失资料和同分排序正确；
- AI 超时或关闭时，发布、匹配和沟通仍可用；
- 注销、隐藏名片和举报路径可执行；
- 日志和错误响应不包含凭证、密钥或敏感正文。

## 4. 前端要求

- 每个异步页面覆盖 loading、success、empty、error 和 retry；
- 表单覆盖必填、长度、枚举、重复提交和离开未保存提醒（适用时）；
- 不只测试按钮隐藏，越权响应必须有正确处理；
- 关键页面在目标微信开发者工具和至少一台真实设备验证；
- UI 截图只证明视觉状态，不能替代行为断言。

## 5. 后端要求

- 业务服务单元测试不依赖网络；
- Repository/ORM 与真实测试数据库验证约束和事务；
- 每个资源接口至少覆盖所有者、非所有者、未认证和资源不存在；
- 外部服务使用受控 stub，覆盖超时、限流、无效响应和重试上限；
- 数据迁移同时验证空库和已有数据升级路径。

## 6. 推荐模型、生成式 AI 与匹配

- 匹配分数来自确定性规则，使用固定样本的 golden tests；
- 轻量模型使用固定特征 schema 和可复现数据快照，验证时间切分、标签版本、随机种子和模型校验和；
- 离线测试必须与规则基线比较，并覆盖冷启动、特征缺失、特征版本不匹配和模型加载失败回退；
- 影子测试比较规则与模型输出但不影响用户，小流量启用后同时观察业务结果、举报/拉黑率和延迟；
- 测试必须证明模型不能召回被硬约束过滤的候选；
- AI 解释测试验证结构、敏感信息、事实约束和降级，不要求字句完全相同；
- 在线模型评估放在独立、可选流程，记录模型和提示版本、样本和人工评分；
- CI 不因外部模型偶发不可用而阻塞 P0，但 AI 网关自身契约和降级测试必须通过。

## 7. 测试数据

- 使用合成身份和内容，不使用真实学生私信、微信身份或联系方式；
- 工厂数据覆盖三类用户、公开/私有资料、不同时间、项目阶段和治理状态；
- 测试应独立并可重复，禁止依赖固定执行顺序；
- 安全测试输出也需脱敏。

## 8. 合并门槛

工程初始化后，在此登记每类改动对应的精确命令。最低要求：

- 相关单元/组件测试通过；
- 契约变更的契约测试通过；
- 数据变更的迁移测试通过；
- lint、类型检查和构建通过；
- P0 主链路变更通过对应 E2E；
- 任务文件和评审记录中写明实际命令、结果和未覆盖风险；使用 PR 时同步引用这些记录。

覆盖率阈值在工具链建立和首批测试完成后确认，不得为了达标编写无断言测试。
